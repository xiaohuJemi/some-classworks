# 学生综合素质测评填表 Skill

## 目标

收到以下材料后，直接完成“识别规则 → 核验材料 → 计算分数 → 填写原表 → 校验结果 → 输出成品表格”的闭环：

1. 综合素质测评总条例、学院/年级实施细则、当年补充通知；
2. 待填写的 Word / Excel / 其他可编辑登记表；
3. 成绩、排名、竞赛证书、项目材料、论文、专利、外语考试、任职/考核、志愿时长、文体活动、集体荣誉等证明；
4. 用户补充的关键信息，例如身份字段、成员排序、项目状态与等级、任职时长、考核等级、成绩等。

最终输出：**已经计算并填写完成的表格文件**。除非用户另有要求，不额外制作无关报告。

## 一、规则优先级

先确定“哪份规则控制哪一项”，禁止凭常识补规则。

优先级通常为：

**当学年/当次测评最新补充通知 > 学院或年级实施细则 > 学校总条例 > 用户明确要求的特殊核算口径。**

若文件明确写明其他优先关系，以文件为准。

当规则冲突时：
- 不自行平均或折中；
- 优先使用更具体、更新、适用于当前学生所在学院/年级的规则；
- 若仍无法判断，列为“待确认项”，一次性向用户询问。

用户如果明确要求“某项按可计分处理”“按某个等级计算”，可以按用户指定口径填写，但要在内部核算记录中标记为“用户确认口径”，不得伪装成文件原文要求。

## 二、先建立测评结构

读取规则后，先整理成一张内部计算表，至少包含：

| 模块 | 子项 | 原始值/事实 | 规则 | 系数/上限 | 计算结果 | 证据 | 状态 |
|---|---|---:|---|---:|---:|---|---|
| 基础素质 | 德育 | … | … | … | … | … | 已确认/待确认 |
| 发展素质 | 学科竞赛 | … | … | … | … | … | … |

必须先确认８j- 基础素质和发展素质的组成；
- 德智体美劳各自权重；
- 最终综合素质总分公式；
- 各分项是否有最低要求、封顶、折算、重复加分限制；
- 排名、团队排序、项目角色、比赛级别、结题等级等是否改变加分。

## 三、基础素质计算

按文件逐项计算，不省略中间公式。

常见结构包括但不限于：
- 德育：思政课成绩 × 权重 + 班级民主评议 × 权重；
- 智育：课程成绩按学分加权；
- 体育：体测成绩与体育课成绩加权；
- 美育：美育课程与民主评议加权，或按当年规定直接取民主评议；
- 劳育：劳动课程与民主评议加权。

若某原始单元格因外链公式损坏，但总分和其他分项均确定，可用公式反推；必须在内部记录标注“反推值”，不能当作原始证明值。

## 四、发展素质材料识别

对每一份证明材料，提取并记录：

- 项目/奖项/活动全称；
- 日期及所属测评学年；
- 级别：国家、省部、市校、院级等；
- 等次：特等奖、一等奖/金奖、二等奖/银奖、三等奖/铜奖、优秀、良好、合格等；
- 本人角色：负责人、第一主持人、第二主持人、成员、作者排序、发明人排序、班委身份等；
- 是否团队项目；
- 是否与另一项属于同一作品/同一项目/同一事项；
- 是否需要结题、授权、通过实审、服务满一年等前置条件；
- 是否存在最高分、折半、比例系数或封顶。

材料中的名字、学号、项目名称要与本人信息交叉核验。

## 五、重复项目与去重

这是最容易算错的部分，必须主动检查。

遇到同一作品/项目参加不同级别比赛：
1. 先查规则是否规定“最高奖×1.2”“只取最高”“可以累计”等；
2. 同一项目不得在违反规则的情况下重复累加；
3. 不同作品/不同项目，若规则允许，可分别计分；
4. 金/银/铜与一/二/三等奖的映射按文件执行；
5. 特等奖、名次奖的换算按文件执行；
6. 团队获奖时，根据证书排序或主管单位证明应用第一名、第二三名、第四至第七名等系数；
7. “团队整体不分先后”与“证书列有顺序”不可混为一谈。

在最终填写前，必须做一次“同名项目 + 相似项目名 + 同作品不同赛事”的重复检查。

## 六、创新创业项目

必须区分：
- 立项；
- 结题合格；
- 结题良好；
- 结题优秀。

按规则确定国家/省部/校市/院级基准分，再根据负责人、第二/第三成员、其他成员等系数计算。

如果立项和结题发生在同一学年且规则规定取高，不得重复计算。

若用户只说“有项目”，但没有说明立项还是结题、结题等级或本人角色，而这些信息会改变得分，必须一次性询问。

## 七、专利、论文、外语与其他项目

### 专利
核验：专利类型、申请人/专利权人、本人的发明人排序、受理/实审/授权状态、专业相关性要求。

如果规则要求授权，但用户明确要求“按能计分处理”，可按用户指定口径计算，同时在内部记录中标明该假设。

### 论文
核验：刊物级别、是否正式发表、作者排序、是否限前三名、论文集系数、获奖系数、同文是否重复。

### 外语
按规则所列考试类别、实际分数与门槛计分。登记表若要求填写具体分数，优先写具体数字，不只写“通过”。

### 公共服务
核验：
- 校/院/班级；
- 主要负责或非主要负责；
- 考核优秀/良好/合格；
- 任职是否满一年；
- 半年以上不满一年是否需要乘系数；
- 同时多个职务是否允许累计。

### 志愿服务
区分“志愿时长加分”和“志愿服务获奖加分”。达到时长门槛前通常不得擅自按比例折算。

### 集体荣誉/班集体
确认本人属于主要负责人、其他负责人还是普通成员。具体职务分类如规则另有定义，严格套用。

## 八、缺失信息处理

只询问**会影响最终得分或表格必填字段**的信息。

不要每发现一个缺口就问一次。先把全部材料读完，再汇总成一次问题，例如：

> 还缺 4 项：外语考试具体分数；创新项目的结题等级；公共服务任职是否满规定时长；集体中的具体职务。其余空白项若确认没有，我按0填写。

如果用户明确说“其他没有”，则剩余可选加分项直接按0处理，不再反复追问。

## 九、计算与校验

完成所有项目后至少做四层校验：

1. **算术校验**：分项和、权重、乘数、封顶；
2. **规则校验**：是否满足前置条件、是否重复加分；
3. **材料校验**：姓名、学号、项目、排序、等级是否对应本人；
4. **表格校验**：所有应填单元格是否已填，公式结果是否与文字一致。

常见总分逻辑：

- 基础素质得分 J = 德育×权重 + 智育×权重 + 体育×权重 + 美育×权重 + 劳育×权重；
- 发展素质得分 F = 德育发展×权重 + 智育发展×权重 + 体育发展×权重 + 美育发展×权重 + 劳育发展×权重；
- 综合素质得分 Z = J×基础占比 + F×发展占比。

**只能使用用户提供规则中的实际权重，不能默认上述具体比例。**

## 十、填写表格

用户提供原始 Word/Excel 模板时：

- 优先直接修改原文件的副本；
- 尽可能保持原有字体、字号、合并单元格、列宽、分页、边框和版式；
- 不自行重做一张风格不同的新表；
- 身份字段（如姓名、学号/编号、班级/组织等）仅从本次用户提供的待填表或明确输入中读取，并写入指定位置；
- 分项名称尽量使用证书或文件中的正式名称；
- 需要多个项目写入同一单元格时，按模板可读性换行；
- 用户本人签名栏默认留空，除非用户明确要求填入电子签名文本；
- 0分项目：若模板习惯为空则保持空白，若模板要求完整填写则填“0”。根据同一表格现有风格判断。

如果原模板是：
- `.xlsx`：输出填写后的 `.xlsx`；
- `.docx`：输出填写后的 `.docx`；
- 只有图片/PDF且不可编辑：先询问用户希望生成 Word 还是 Excel，除非已有明确偏好。

## 十一、最终输出

完成后只需简流说明：

- 已完成填写；
- 最终基础素质、发展素质、综合素质得分；
- 仍存在的“用户指定口径”或“审核风险项”（如有）；
- 提供成品文件下载链接。

不要把长篇规则重新抄给用户，除非用户要求核算明细。

## 十二、隐私与发布安全

- Skill 本体不得固化任何真实个人姓名、学号/编号、班级、学校/学院、电话号码、邮箱、地址、证件号、专利/申请号、项目名、成绩或其他可关联到具体个人/组织的案例数据；
- 不把用户上传的证明材料、截图、证书、成绩单或填好的个人表格打包进 Skill；
- 示例只能使用抽象占位描述，不得复用真实案例中的项目名、赛事名组合、具体个人角色组合或唯一性很强的事实；
- 在公开仓库、公开分享或导出可复用 Skill 前，扫描文本、文件名、压缩包清单及文档元数据，确认不存在个人信息、机构内部信息、账号凭据、访问令牌或本地路径；
- 运行时可以读取用户当次提供的身份信息用于填表，但这些信息不得写回 Skill 源码或作为默认值长期保留。

## 十三、禁止事项

- 禁止根据经验猜测竞赛级别、项目等级、成员排序；
- 禁止把“受理”自动当成“授权”，除非规则或用户明确允许；
- 禁止同一项目重复累计违反规则的奖项；
- 禁止漏掉团队成员排序系数；
- 禁止把用户口头说“通过”擅自改成某个具体分数；
- 禁止在材料不支持时自行补造证据；
- 禁止在用户已说明“其他没有”后继续逐项反复追问；
- 禁止只给计算过程而不输出填写完成的表格。

## 十四、推荐内部工作流

按以下顺序执行：

**A. 读取全部规则 → B. 读取待填模板 → C. 扫描所有证明材料 → D. 建立证据/计分台账 → E. 查重与规则映射 → F. 汇总一次性缺失信息 → G. 计算 → H. 二次校验 → I. 填写原表 → J. 渲染/检查版式 → K. 输出最终文件。**

除非规则或用户要求变化，不要打乱这个顺序。
